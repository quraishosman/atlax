# ADR-009: Staged PostgreSQL Repository Cutover

Status: Accepted
Date: 2026-08-09

## Context

ATLAX currently stores business state across JSON files and SQLite databases.
Google Cloud SQL for PostgreSQL is the approved shared production target, but
changing one store at a time would allow the scanner, Telegram bot, API, and
dashboard to observe different versions of payment, subscription, signal, or
audit state.

## Decision

Implement explicit PostgreSQL repository adapters first, verify them with
dual-read comparisons, and only then wire every component to the shared
repository interface in one controlled release.

Repository writes are row-level and transaction-scoped. Mutable records use
monotonic timestamps so an older migration snapshot cannot overwrite a newer
remote row. Payment and subscription repositories do not expose destructive
snapshot replacement operations.

The local backend remains the default until the complete repository set is
wired and the cutover gates in `docs/24_POSTGRES_REPOSITORY_CUTOVER_PLAN.md`
are satisfied.

## Consequences

- Migration requires more than setting an environment variable, but prevents
  partial storage cutovers.
- Local files remain available as a rollback copy during the verification
  window.
- PostgreSQL adapter tests can run independently before production wiring.
- Cloud SQL provisioning is a deployment task after repository cutover, not a
  substitute for application consistency.
