# ADR-005: Telegram Terminal UX And Future Mini App

Status: Accepted  
Date: 2026-08-08

## Context

The first Telegram experience exposed a plain status message and a small set of menu actions. ATLAX needs a more useful onboarding and subscriber terminal while preserving its deterministic trading architecture.

BONKbot demonstrates a strong interaction pattern for Telegram products: persistent account state, quick actions, real-time alerts, and progressive navigation. ATLAX must adapt that pattern to signal delivery, profile preferences, subscription access, market context, and advisory analytics.

Telegram inline keyboards are suitable for quick navigation. A richer signal terminal, charts, analytics, and profile editing will eventually be better served by the existing dashboard running as a Telegram Mini App.

## Decision

ATLAX will use a two-layer Telegram experience:

1. A chat-first terminal for onboarding, access status, profile actions, subscriptions, recent signals, market context, help, and admin review actions.
2. A future Mini App that reuses the dashboard for dense data, charts, analytics, and richer settings.

Phase 1 will use existing backend sources only:

- `SubscriberDB` for identity, access, style, timeframes, symbols, confidence, and notification preferences.
- `PaymentService` for subscription and payment state.
- Existing alert and prediction records for read-only signal summaries.
- Existing market, analytics, and advisory services for their documented views.

The Telegram experience must not define CRT rules, calculate new trading decisions, override risk, or execute trades. Telegram callbacks are presentation and preference actions, not a new strategy layer.

## Security Requirements

- Server-side chat identity and role checks are required for every state-changing action.
- Admin actions must fail closed for non-admin users.
- Callback data must be allow-listed and logged without secrets.
- Payment confirmation remains behind the approved payment workflow in ADR-004.
- A future Mini App must validate Telegram `initData` on the backend and must not trust `initDataUnsafe`.
- The Mini App must not store long-lived bearer tokens in browser `localStorage`.

## Consequences

- New users receive a useful personalized entry point instead of a bare command response.
- Returning users can reach profile, subscription, signal, market, and support actions without memorizing commands.
- The initial implementation stays compatible with the current scanner and alert pipeline.
- Telegram presentation code should be extracted from `MarketScanner` as the terminal grows, while the scanner remains the system orchestrator.
- The dashboard becomes the preferred long-form Telegram interface once Mini App hosting and authentication are approved.

## Out Of Scope

- Solana wallet custody or private-key handling.
- BONKbot-style token trading, limit orders, DCA, trailing stops, or MEV routing.
- Automatic payment verification without an approved provider adapter.
- AI-generated live entries, exits, confidence scores, risk decisions, or execution.
